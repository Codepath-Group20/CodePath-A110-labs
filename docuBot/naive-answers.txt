If you are integrating with services like Google, GitHub, or Microsoft:
* **Where it happens:** The token is generated by the external provider's **Authorization Server** at their designated token endpoint (usually `/oauth/token` or `/token`) after the user approves the login request.

Question: What environment variables are required for authentication?

Answer:
To give you the most accurate answer, **it helps to know which framework, library, or identity provider you are using** (e.g., NextAuth.js, Supabase, Auth0, Firebase, or a custom JWT setup). 

However, because authentication requirements vary by stack, here is a breakdown of the required environment variables for the most common authentication setups:

---

### 1. Custom JWT / Token-Based Authentication (Node.js, Express, Django, etc.)
If you are building your own authentication backend using JSON Web Tokens (JWT), you typically need:

```env
JWT_SECRET=your_super_secret_jwt_key_here  # Used to sign and verify tokens
JWT_EXPIRES_IN=1d                          # (Optional) Token lifespan (e.g., 24h, 7d)
```

---

### 2. NextAuth.js / Auth.js (Next.js Framework)
For Next.js applications using NextAuth.js, the minimal required variables are:

```env
NEXTAUTH_SECRET=your_nextauth_secret_key   # Used to encrypt cookies and tokens
NEXTAUTH_URL=http://localhost:3000         # The canonical URL of your site (production/local)
```

---

### 3. Third-Party Identity Providers (SaaS)
If you are outsourcing authentication to a third-party service, you will need keys provided in their respective developer dashboards:

#### **Clerk**
```env
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...
```

#### **Supabase**
```env
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=your_anon_public_key
SUPABASE_SERVICE_ROLE_KEY=your_admin_secret_key # Keep secure, never expose to client
```

#### **Auth0**
```env
AUTH0_SECRET=use_a_long_random_value_here
AUTH0_BASE_URL=http://localhost:3000
AUTH0_ISSUER_BASE_URL=https://your-tenant.auth0.com
AUTH0_CLIENT_ID=your_client_id
AUTH0_CLIENT_SECRET=your_client_secret
```

---

### 4. OAuth Social Logins (Google, GitHub, Apple, etc.)
If you are enabling "Sign in with [Provider]", you must register your app on the provider's developer console to obtain these:

```env
# Google Example
GOOGLE_CLIENT_ID=your_google_client_id
GOOGLE_CLIENT_SECRET=your_google_client_secret

# GitHub Example
GITHUB_ID=your_github_client_id
GITHUB_SECRET=your_github_client_secret
```

---

### 💡 Best Practices for Environment Variables:
1. **Never commit secrets to Git:** Ensure your `.env` file is added to your `.gitignore` file.
2. **Use `.env.example`:** Commit a template file (e.g., `.env.example`) with empty values so other developers know what variables are required.
3. **Prefixing Client vs. Server:** 
   * In frameworks like Next.js, keys prefixed with `NEXT_PUBLIC_` are accessible to the browser. **Never** prefix database secrets, private keys, or admin keys with `NEXT_PUBLIC_`.

Question: How do I connect to the database?

Answer:
To give you the exact code and steps, I’ll need to know **which database** (e.g., PostgreSQL, MySQL, MongoDB, SQLite) and **which programming language/framework** (e.g., Node.js, Python, Java, PHP) you are using.

However, almost all database connections require the same fundamental information and follow a similar pattern. Here is a general guide and a few common examples.

---

### 1. The General Information You Need
To connect to any database, you will typically need a **Connection URI/String** or the following individual credentials:
*   **Host:** Where the database is running (e.g., `localhost` or `127.0.0.1` for local, or an IP/domain for cloud databases).
*   **Port:** The port the database listens on (e.g., `5432` for PostgreSQL, `3306` for MySQL, `27017` for MongoDB).
*   **Username & Password:** Your database credentials.
*   **Database Name:** The specific database you want to query.

A standard connection URI looks like this:
`mongodb://username:password@host:port/database_name` or `postgresql://username:password@host:port/database_name`

---

### 2. Common Examples

#### **Option A: Node.js (JavaScript/TypeScript) to PostgreSQL**
Using the popular `pg` library:

1. Install the package:
   ```bash
   npm install pg
   ```
2. Connect in your code:
   ```javascript
   const { Client } = require('pg');

   // Use a connection string
   const client = new Client({
     connectionString: "postgresql://user:password@localhost:5432/my_database",
   });

   async function connectDB() {
     try {
       await client.connect();
       console.log("Connected successfully to PostgreSQL!");
     } catch (err) {
       console.error("Connection error", err.stack);
     }
   }

   connectDB();
   ```

#### **Option B: Python to PostgreSQL**
Using the `psycopg2` library:

1. Install the package:
   ```bash
   pip install psycopg2-binary
   ```
2. Connect in your code:
   ```python
   import psycopg2

   try:
       connection = psycopg2.connect(
           host="localhost",
           database="my_database",
           user="my_username",
           password="my_password",
           port="5432"
       )
       print("Connected successfully to PostgreSQL!")
       
       # Close connection when done
       connection.close()
   except Exception as error:
       print(f"Error connecting to database: {error}")
   ```

#### **Option C: Node.js to MongoDB (NoSQL)**
Using the `mongoose` ODM:

1. Install mongoose:
   ```bash
   npm install mongoose
   ```
2. Connect in your code:
   ```javascript
   const mongoose = require('mongoose');

   const uri = "mongodb://localhost:27017/my_database";

   mongoose.connect(uri)
     .then(() => console.log("Connected successfully to MongoDB!"))
     .catch(err => console.error("Database connection error:", err));
   ```

Question: How does a client refresh an access token?

Answer:
To refresh an expired access token, a client application performs a **Refresh Token Flow** (defined in the OAuth 2.0 framework). This allows the client to obtain a new access token without requiring the user to log in again.

Here is a step-by-step developer guide on how this process works.

---

### The Flow at a Glance

1. **Access Token Expires:** The client attempts to make an API call, and the API returns a `401 Unauthorized` status (often with an expired token error).
2. **Refresh Request:** The client sends a `POST` request to the Authorization Server's token endpoint.
3. **Token Verification:** The server validates the refresh token and client credentials.
4. **New Tokens Issued:** The server responds with a new access token (and optionally a new refresh token).

---

### Step 1: Send the Refresh Request

The client must make an HTTP `POST` request to the Identity Provider's token endpoint (usually `/oauth/token` or `/v1/token`). 

The request body must be encoded as `application/x-www-form-urlencoded` and contain the following parameters:

*   **`grant_type`**: Must be set to `refresh_token`.
*   **`refresh_token`**: The refresh token previously issued to the client.
*   **`client_id`**: The client's application ID.
*   **`client_secret`**: (Only required for confidential clients, like web servers. Public clients like SPAs or mobile apps should not use a client secret).

#### Example HTTP Request

```http
POST /oauth/token HTTP/1.1
Host: authorization-server.com
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&
refresh_token=rT4b_x9LpZ2...&
client_id=YOUR_CLIENT_ID&
client_secret=YOUR_CLIENT_SECRET
```

---

### Step 2: Handle the Response

If the refresh token is valid and has not been revoked, the authorization server will return a `200 OK` response containing the new tokens in JSON format.

#### Example Successful Response

```json
{
  "access_token": "eyJhbGciOi...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "gP5e_z2WsX9...", 
  "scope": "read write"
}
```
> **Note:** A new `refresh_token` may or may not be returned. If a new one is returned, you **must** discard the old one and save the new one (this is known as *Refresh Token Rotation*).

#### Example Error Response
If the refresh token has expired, been revoked, or is invalid, the server will return a `400 Bad Request` or `401 Unauthorized` response:

```json
{
  "error": "invalid_grant",
  "error_description": "The refresh token is invalid or expired"
}
```
*If you receive an `invalid_grant` error, you must clear the stored tokens and redirect the user to log in again.*

---

### Implementation Example (JavaScript/Fetch)

Here is how you might implement this in JavaScript:

```javascript
async function refreshAccessToken(storedRefreshToken) {
  const tokenEndpoint = "https://authorization-server.com/oauth/token";
  
  const payload = new URLSearchParams({
    grant_type: "refresh_token",
    refresh_token: storedRefreshToken,
    client_id: "YOUR_CLIENT_ID"
  });

  try {
    const response = await fetch(tokenEndpoint, {
      method: "POST",
      headers: {
        "Content-Type": "application/x-www-form-urlencoded",
      },
      body: payload,
    });

    if (!response.ok) {
      const errorData = await response.json();
      throw new Error(errorData.error_description || "Failed to refresh token");
    }

    const data = await response.json();
    
    // Save the new access token (and new refresh token if provided)
    saveTokens(data.access_token, data.refresh_token);
    
    return data.access_token;
  } catch (error) {
    console.error("Token refresh failed. Redirecting to login...", error);
    forceUserLogin();
  }
}
```

---

### Security Best Practices

1. **Secure Storage:** 
   * **Web Apps (SPAs):** Avoid storing refresh tokens in `localStorage` due to XSS vulnerability. Instead, store them in secure, `HttpOnly`, `SameSite=Strict` cookies.
   * **Mobile/Desktop:** Store them in secure OS-level storage (e.g., iOS Keychain, Android Keystore).
2. **Refresh Token Rotation (RTR):** Always implement RTR if your auth provider supports it. Every time you use a refresh token, the server sends back a *new* refresh token and invalidates the old one. This detects and prevents token theft.
3. **Sliding Expiration:** Refresh tokens should have an absolute expiration time (e.g., 30 days) after which the user must log in again regardless of activity.
